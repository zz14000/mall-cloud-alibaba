# 前台会员登录与后台管理员登录对比分析

## 一、相同点

### 1. 认证流程相同
- 都使用 Spring Security 框架
- 都通过 `loadUserByUsername()` 加载用户信息
- 都使用 `PasswordEncoder` 验证密码
- 都使用 `JwtTokenUtil` 生成 JWT Token
- 都使用 `SecurityContextHolder` 临时存储认证信息

### 2. 技术栈相同
- 都使用 JWT 进行身份认证
- 都实现了 `UserDetails` 接口封装用户信息
- 都使用 Redis 缓存用户信息

### 3. 登录方法签名相似
```java
// 会员登录
public String login(String username, String password)

// 管理员登录
public String login(String username, String password)
```

---

## 二、核心差异

| 对比维度 | 前台会员登录 | 后台管理员登录 |
|---------|------------|--------------|
| **UserDetails 实现** | `MemberDetails` | `AdminUserDetails` |
| **权限来源** | 硬编码 `"TEST"` | 从数据库动态加载资源列表 |
| **权限粒度** | 无权限控制 | 基于 RBAC 的细粒度权限控制 |
| **缓存内容** | 只缓存会员基本信息 | 缓存管理员信息 + 资源列表 + Token |
| **登录日志** | ❌ 不记录 | ✅ 记录到 `ums_admin_login_log` |
| **Token 存储** | ❌ 不保存到 Redis | ✅ 保存到 Redis（支持登出、失效） |
| **数据表** | `ums_member` | `ums_admin` + `ums_admin_login_log` |

---

## 三、关键代码对比

### 1. 权限获取方式

**会员（硬编码）：**
```java
// MemberDetails.java
@Override
public Collection<? extends GrantedAuthority> getAuthorities() {
    return Arrays.asList(new SimpleGrantedAuthority("TEST"));
}
```

**管理员（动态加载）：**
```java
// AdminUserDetails.java
@Override
public Collection<? extends GrantedAuthority> getAuthorities() {
    // 从数据库查询的资源列表转换为权限
    return resourceList.stream()
            .map(role -> new SimpleGrantedAuthority(role.getId()+":"+role.getName()))
            .collect(Collectors.toList());
}
```

### 2. Token 处理

**会员登录：**
```java
// UmsMemberServiceImpl.java
token = jwtTokenUtil.generateToken(userDetails);
// ❌ 没有保存到 Redis
```

**管理员登录：**
```java
// UmsAdminServiceImpl.java
token = jwtTokenUtil.generateToken(userDetails);
// ✅ 保存到 Redis，支持登出、失效等操作
adminCacheService.setToken(username, tokenHead+token);
insertLoginLog(username); // 记录登录日志
```

### 3. UserDetails 加载

**会员：**
```java
@Override
public UserDetails loadUserByUsername(String username) {
    UmsMember member = getByUsername(username);
    if (member != null) {
        return new MemberDetails(member);
    }
    throw new UsernameNotFoundException("用户名或密码错误");
}
```

**管理员：**
```java
@Override
public UserDetails loadUserByUsername(String username){
    //获取用户信息
    UmsAdmin admin = getAdminByUsername(username);
    if (admin != null) {
        // 获取该管理员通过角色关联能访问的所有 API 资源列表
        List<UmsResource> resourceList = getResourceList(admin.getId());
        return new AdminUserDetails(admin, resourceList);
    }
    throw new UsernameNotFoundException("用户名或密码错误");
}
```

## 四、为什么会员登录不需要保存 Token 到 Redis？

### 原因分析：

#### 1. 业务需求不同
- **后台管理员**：需要支持强制登出、权限变更立即生效、登录审计等功能
- **前台会员**：通常不需要强制用户下线，权限简单（只有普通用户）

#### 2. Token 失效策略不同
- **管理员**：Token 存 Redis，可以通过删除 Redis key 实现：
  - 主动登出
  - 账号禁用立即失效
  - 权限修改后立即生效
- **会员**：依赖 JWT 的过期时间，不主动失效

#### 3. 安全性要求不同
- **后台**：涉及商品管理、订单处理等敏感操作，需要严格管控
- **前台**：主要是浏览商品、下单等常规操作，安全性要求相对较低

#### 4. 性能考虑
- **会员系统**：用户量大，如果每个用户 Token 都存 Redis，会增加 Redis 压力
- **后台系统**：管理员数量有限，存储 Token 的成本可接受

## 五、架构图

### 会员登录流程
```
会员登录请求
    ↓
UmsMemberServiceImpl.login()
    ↓
loadUserByUsername(username)
    ↓
查询 ums_member 表
    ↓
构建 MemberDetails（权限固定为"TEST"）
    ↓
验证密码
    ↓
生成 JWT Token
    ↓
返回 Token（不存 Redis）
```

### 管理员登录流程
```
管理员登录请求
    ↓
UmsAdminServiceImpl.login()
    ↓
loadUserByUsername(username)
    ↓
查询 ums_admin 表
    ↓
查询 ums_admin_role_relation 表（获取角色）
    ↓
查询 ums_role_resource_relation 表（获取资源）
    ↓
构建 AdminUserDetails（动态权限）
    ↓
验证密码
    ↓
生成 JWT Token
    ↓
Token 存入 Redis（支持登出、失效）
    ↓
记录登录日志到 ums_admin_login_log
    ↓
返回 Token
```

## 六、总结

这个设计体现了**按需设计**的原则：

| 系统 | 设计特点 | 适用场景 |
|------|---------|---------|
| **后台管理员** | Token 存 Redis + 登录日志 + 动态权限 | 需要强管控、高安全性 |
| **前台会员** | JWT 自包含 + 硬编码权限 + 不记录日志 | 轻量级认证、用户量大 |

### 如果需要增强会员系统安全性

可以参考后台的实现，将会员 Token 也保存到 Redis 中，支持：
- 封号处理
- 强制下线
- 权限动态控制
- 登录行为审计
